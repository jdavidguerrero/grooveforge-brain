# CI de la consola — G21

La CI valida regresiones de software desde un checkout limpio: compilar detecta
errores de integración entre headers, librerías y toolchains; los tests nativos
validan comportamiento sin atribuirle cobertura del hardware. El alcance parte de
[G21](auditoria/auditoria-fable-2026-11.md) y de la sección Testing de `CLAUDE.md`.
No cambia contratos de audio ni protocolos.

Se amplía `.github/workflows/ci.yml` para conservar los checks existentes y tener
una sola definición de triggers, filtros y dependencias compartidas. Una matriz
usa `fail-fast: false`: un entorno que falla no cancela los demás.

## Qué corre

| Job | Runner | Validación |
|---|---|---|
| `changes` | Ubuntu | Determina componentes afectados con el diff Git local |
| `build-teensy` | Ubuntu, Python 3.11 | `sketch`, `sketch49`, `consola`, `consola_usb`, `consola_uno`, `consola_hw_test` |
| `test-native` | Ubuntu, Python 3.11 | Unity native de Teensy, ESP32 y processor |
| `build-esp32` | Ubuntu, Python 3.11 | Firmware `esp32s3` |
| `build-processor` | Ubuntu, Python 3.11 | `consola_s`, `consola_s_m4`, GroovePush `teensy41` y `neotrellis_m4` |
| `test-tools` | Ubuntu, Python 3.14 | pytest de consola, motor y perc-synth, cada uno con su `uv.lock` |
| `test-gui` | Ubuntu, Python 3.14 | PySide6/QML offscreen, incluido host real compilado en un directorio temporal |
| `test-synth-host` | Ubuntu, Python 3.14 | Build Release offline, metadata y CTest |
| `build-pipewire` | Ubuntu con contenedor Debian trixie | Build con SDK PipeWire ≥1.4; comprueba que `GF_HAVE_PIPEWIRE` esté definido |
| `test-brain-plugin` | Ubuntu, Python 3.14 | Targets sin JUCE, `gf_engine_bench` y CTest |
| `test-ml` | Ubuntu, Python 3.11 | Tests existentes de training |

PipeWire necesita ≥1.4 según `16-synth-host.md`. El contenedor trixie proporciona
esa línea de SDK independientemente de la imagen `ubuntu-latest`. Se instala
`libpipewire-0.3-dev` y se exige la versión antes de configurar: CMake puede
desactivar silenciosamente un backend opcional si el SDK es antiguo. También se
inspecciona la definición de compilación para evitar un falso verde offline.

## Disparadores y filtros

- Pull requests cuyo destino sea `main`.
- Push a `main` (compatibilidad), `claude/monorepo-groovepush` y `codex/**`.
- `workflow_dispatch` ejecuta todas las matrices, sin aplicar filtros.

Los workflows arrancan aun para cambios documentales; `changes` omite jobs sin
dependencias afectadas. Cambiar `ci.yml` ejecuta todo. Los filtros incluyen fuentes
compartidas: Bridge → firmwares/engines/host; surface y processor → Teensy único;
engines Teensy y brain-plugin → synth-host y GUI; gemelo-baseline → CTest del plugin. Cambios en perc-synth, paleta-lab o
preset-librarian vuelven a probar motor y consola porque los importan.
Los tests Bridge siguen ejecutándose en cada PR y en cada ejecución manual,
incluso si solo cambió documentación, como exige `CLAUDE.md`.
El filtro usa Git local con historial completo, sin llamadas a la API de GitHub;
no ejecuta código del PR con `pull_request_target`.

Las cachés guardan descargas pip/uv y paquetes/plataformas de PlatformIO. No se
cachean `.pio/build`, `.pio/libdeps`, frameworks privados, `.venv` ni builds CMake.
Así se recompila todo y el symlink `lib_deps` apunta al checkout actual. Cada
entorno USB reconstruye su overlay desde el vendor versionado; nunca modifica el
framework instalado. CI preinstala `teensy@5.1.0` sin dependencias opcionales
(AVR): el build descarga solo las necesarias para la placa. Esa plataforma declara
Teensyduino `~1.160.0`, y el pre-script exige exactamente `1.160.0`. Se comprueban
versión y hashes de los archivos del overlay. Así una caché local con una
plataforma antigua no oculta un cambio del framework en CI.

## Reproducir localmente

Usar un checkout descartable del commit que se quiere validar (con `.git`, pues
los smoke tests del gemelo registran `git rev-parse HEAD`). No reutilizar builds.

```bash
python3.11 -m pip install platformio==6.2.0
pio pkg install --global --platform platformio/teensy@5.1.0 --skip-dependencies
cd apps/firmware-teensy
pio run -e sketch -e sketch49 -e consola -e consola_usb -e consola_uno -e consola_hw_test
pio test -e native
cd ../firmware-esp32
pio run -e esp32s3
pio test -e native
cd ../consola/processor
pio run -e consola_s -e consola_s_m4 -e teensy41 -e neotrellis_m4
pio test -e native
```

En cada uno de `tools/consola`, `tools/motor`, `tools/perc-synth`:

```bash
uv run --python 3.14 --frozen pytest
```

En `apps/training`: `uv sync --python 3.11 --frozen`, seguido de
`uv run --frozen pytest --tb=short`.

Desde la raíz, con Python 3.14 y `PySide6>=6.8`, `pytest>=8` instalados:

```bash
QT_QPA_PLATFORM=offscreen QT_QUICK_BACKEND=software python3 -m pytest apps/consola/gui-console/tests -q
cmake -S apps/synth-host -B build/synth-host -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON -DGF_HOST_PIPEWIRE=OFF -DGF_HOST_JACK=OFF
cmake --build build/synth-host --parallel 2
ctest --test-dir build/synth-host --output-on-failure --timeout 120
cmake -S apps/brain-plugin -B build/brain-plugin -DCMAKE_BUILD_TYPE=Release -DGF_BUILD_VST3=OFF -DGF_BUILD_ENGINE_BENCH=ON
cmake --build build/brain-plugin --parallel 2
ctest --test-dir build/brain-plugin --output-on-failure --timeout 120
```

Host/GUI requieren CMake ≥3.22, compilador C++17, pkg-config y json-c
(`brew install cmake pkg-config json-c` en Mac; `libjson-c-dev` en Ubuntu).
GUI Linux necesita además `libegl1`, `libgl1` y `libxkbcommon0` aunque sea offscreen.
Los jobs Python de audio instalan `libasound2-dev`, `libjack-jackd2-dev`,
`libportaudio2` y `libsndfile1` para los bindings MIDI/audio; no necesitan dispositivos.

Para comprobar instalación sin cachés, fijar `PLATFORMIO_CORE_DIR` y `UV_CACHE_DIR`
a directorios temporales vacíos. Se necesita red para descargar toolchains,
frameworks, librerías y wheels. Nunca apuntarlos al core usado por otra tarea.

## Límites

No cubre flasheo ni USB audio real, panel, MIDI físico, latencia, xruns, CPU/RAM en
Teensy, calidad audible, ni rendimiento térmico/tiempo real en Pi. Compilar
`consola_hw_test` no ejecuta la prueba en placa. PipeWire solo se compila; no se
arranca servidor de audio. No se compila VST3/JUCE ni el oracle MSFA externo.
Las comprobaciones de plantillas personales Ableton de motor también omiten
los casos si esas plantillas no están instaladas.
GeneralSans no está versionada: el test correspondiente conserva su skip; no se
descarga ni copia una fuente local a CI.

Una ejecución completa abre varias matrices y consume más minutos, especialmente
con caché fría de PlatformIO y TensorFlow. Los filtros y límites de tiempo reducen
el costo; las descargas siguen dependiendo de los registros externos. Cambios en
paquetes de sistema o dependencias sin versión exacta pueden requerir mantenimiento.
